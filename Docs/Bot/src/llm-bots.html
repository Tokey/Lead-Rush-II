How the LLM bots work, and what the logs say about them

The bots always aim, move and shoot with LR2's own code, every frame. The LLM is a squad leader on a radio: every few seconds it reads what the team has seen and sends orders back. This page describes that loop as the code runs it, the failure rates measured in real logs, what changed on 11-26, and which study numbers to trust.

The loop

One order cycle

1 · Team pictureLLMCommander writes a JSON snapshot: own soldiers (health, armour, ammo, what each is doing), the map bounds and objective, and enemies someone on the team saw in the last 20 s, with who saw them.
2 · SendGroqClient sends one request at a time, at least 2.5 s apart, 15 s timeout, JSON-only replies, up to 700 tokens.
3 · Groq modelgpt-oss-20b, then llama-3.1-8b-instant, then llama-3.3-70b if a model is refused. Avatar Pilot tries the fast 8b model first.
4 · Check the ordersEach order is checked per bot. "Attack" becomes "move to where the enemy was last seen", so the LLM cannot point a bot at someone nobody has seen.
5 · Bots actBotController carries the order out for about 1.6× the order interval. Aim, recoil control and trigger timing stay local and run every frame.

Without an API key the commander warns once, retries the key every 5 s, and the bots play exactly like the rule bots. Keys are read from GROQ_API_KEY, -lr2GroqKeyFile or the key file in the player's data folder, and never written to logs or telemetry.

Reading the 11-23 / 11-24 study

Which numbers hold up

"Commander 5–1 against rule bots"

Weak. Only 4 to 7 of 9 calls succeeded per 75-second match, so bots spent much of each match without orders. Some matchups gave the LLM team better bots than the other side (M2: Regular + LLM against Recruit rule bots), which wins matches on its own.

"LLM bots score 65.1 % human-likeness"

Unverified. Match telemetry recorded the configured LLM mode, not whether the LLM actually answered. A match where every call failed looks the same in the data as one where the LLM led all game.

Order mix (for example "hold 39 %")

Biased. The study log kept only the first 140 characters of each reply, so orders after the first one or two per reply were never counted.

11-26

Fixed, and still open

Fixed in code (compiles; needs a live run)

  • A scene change during a request no longer leaves the client "busy" for the rest of the session. Before, every LLM bot silently turned into a rule bot after a match restart or an experiment's next match.
  • gpt-oss requests ask for low reasoning effort, so the JSON answer fits in the token budget.
  • The study log keeps the whole reply (up to 4,000 characters, properly escaped).

Still open

  • Pace requests by Groq's remaining-tokens header instead of a fixed 2.5 s gap; back off longer after a 429.
  • One shared commander for all solo LLM bots in free-for-all, instead of one per bot.
  • Write the LLM's health into each match's Meta_*.json (requests, answered, rate-limited, orders) so analyses can drop matches where it never ran.
  • Re-run M1-M8 with equal bot tiers on both sides, then redo the order mix and the human-likeness score.
Next run

Getting a clean LLM measurement

  • Use the same difficulty tier on both teams, Commander mode, 12 s interval, so one squad stays under the free tier's token limit.
  • Check the request log before trusting a match: fewer than 70 % answered calls means the bots mostly played without orders.
  • Count orders from the full replies in the new logs, and keep the Off-mode run as the baseline.
